# iApki — Telegram-бот + Mini App

Приём заказов на доступ к каталогу приложений для iPhone: витрина, оплата,
приём UDID, переписка с покупателем и ведение заказа продавцом. Один контейнер
с ботом и веб-приложением плюс Caddy с автоматическим HTTPS.

Воронка: **Оплата → UDID → Установка сертификата → Инструкция**.
Покупатель проходит её в Mini App или прямо в чате; продавец ведёт заказы
кнопками под уведомлениями и во вкладке «Продавец».

## Что внутри

```
app/           бот (aiogram 3) и HTTP-API (aiohttp)
  config.py    все настройки из переменных окружения
  db.py        SQLite: пользователи, заказы, история событий
  service.py   бизнес-правила: один слой для чата и Mini App
  api.py       JSON-API для Mini App + отдача статики
  catalog.py   витрина: товары из сборок в files/ + уточнения из catalog.toml
  bundle.py    что сборка .ipa знает о себе: название, версия, iOS, иконка
  handlers/    buyer.py, seller.py, payments.py (Telegram Stars)
webapp/        Mini App: index.html, styles.css, app.js, icons/
maintenance/   страница техработ для Caddy; включает её ./maintenance.sh
tests/         smoke_test.py (API + правила), bot_test.py (хэндлеры)
tools/         preview.py — локальный предпросмотр UI без Telegram
```

## Запуск на VPS

1. **Бот.** У @BotFather: `/newbot` → токен. Там же `/mybots → Bot Settings →
   Menu Button` можно не трогать: бот сам выставит кнопку меню на Mini App.
2. **Домен.** A-запись на IP сервера, порты 80 и 443 свободны.
3. **Свой Telegram ID** — например через @userinfobot.
4. Скопируйте проект на сервер и заполните `.env`:

```bash
cp .env.example .env
nano .env   # BOT_TOKEN, SELLER_IDS, DOMAIN, WEBAPP_URL, PAYMENT_DETAILS
```

`WEBAPP_URL` должен быть ровно `https://<DOMAIN>` — по нему Telegram откроет Mini App.

### Смена домена

Домен нигде в коде не зашит — он приходит из `.env` и подставляется в Caddy,
в адрес Mini App, в ссылки на документы и в тексты оферты. Чтобы переехать:

```bash
nano .env        # DOMAIN=новый.домен   WEBAPP_URL=https://новый.домен
docker compose up -d   # Caddy получит новый сертификат Let's Encrypt сам
```

Перед этим A-запись нового домена должна указывать на IP сервера, иначе
сертификат не выпустится. Проверка после перезапуска:

```bash
curl -I https://новый.домен/health
```

Бот перечитает `WEBAPP_URL` при старте и переставит кнопку меню на новый адрес.

5. Запуск:

```bash
docker compose up -d --build
```

6. Проверка:

```bash
docker compose logs -f bot
curl -I https://<ваш домен>/
```

В логах должно быть `Бот @имя запущен` и `HTTP слушает 0.0.0.0:8080`.

### Обновление

```bash
git pull && docker compose up -d --build
```

`docker compose down` перед этим не нужен: новый образ собирается, пока старый
бот работает, а потом контейнеры меняются за 5–10 секунд. Всё это время сайт
и Mini App показывают страницу техработ (см. ниже), Telegram копит сообщения,
и бот отвечает на них, как только поднимется.

Правки в `webapp/` подхватываются без пересборки — папка примонтирована в контейнер,
достаточно обновить страницу.

### Технические работы

Когда на сервере нужно поработать дольше — перенос базы, ручные правки,
проверка новой версии, — включите режим техработ:

```bash
./maintenance.sh on      # сайт и Mini App — страница техработ, бот остановлен
# ...git pull, правки .env, работа с базой...
./maintenance.sh off     # собрать бота из текущего кода и вернуть его
./maintenance.sh status  # что сейчас включено
```

- **Сайт и Mini App.** Caddy не останавливается и показывает страницу
  `maintenance/index.html`, пока лежит файл `maintenance/on`, а также всегда,
  когда бот не отвечает (выкатка, падение). Уже открытый Mini App получает
  на запросы к `/api` текст «Идут технические работы». Уведомления Platega
  (`/api/platega/*`) проходят к боту всегда: если бот остановлен, Platega
  повторит их, а бот после включения ещё и сам перепроверит свежие оплаты.
- **Telegram.** Вместо бота работает заглушка (`app/maintenance.py`, сервис
  `maintenance` в профиле compose). На любое сообщение она отвечает, что идут
  техработы, — не чаще раза в минуту на чат, на кнопки — всплывающим окном.
  Сообщения не сохраняются: покупателя просят прислать UDID, чек или вопрос
  ещё раз после работ.
- **Выход.** `off` сначала собирает образ (заглушка в это время отвечает),
  потом меняет заглушку на бота и ждёт строку «Бот @… запущен» в логе — для
  неё нужен `LOG_LEVEL=INFO`. Только после этого страница снимается. Если бот
  за 2 минуты не поднялся, возвращается заглушка, а страница остаётся.
- Пока техработы включены, бота возвращайте только командой `off`: обычный
  `docker compose up` запустит его рядом с заглушкой, и Telegram ответит обоим
  `409 Conflict`.
- Оплату по ссылке Platega, выданной до работ, бот сам находит, если с выдачи
  прошло не больше 40 минут. После более долгих работ покупатель подтвердит её
  кнопкой «Я оплатил — проверить».

Первый раз после обновления, где появился этот режим, Caddy нужно пересоздать
(у него новая папка): это сделает `docker compose up -d --build`. Если скрипт не
запускается, дайте ему право на запуск: `chmod +x maintenance.sh`.

### Бэкап

Вся база — один файл в томе `bot_data`. Достать копию на хост:

```bash
docker compose cp bot:/data/bot.sqlite3 ./backup-$(date +%F).sqlite3
```

База лежит в именованном томе Docker, а не в папке проекта: том наследует
права от образа, поэтому непривилегированный пользователь контейнера может в
него писать. Папка с хоста создаётся от root, и бот такую базу не откроет.

`docker compose down` том сохраняет, `docker compose down -v` — удаляет вместе
со всеми заказами.

### Режимы оплаты

- **manual** (по умолчанию) — покупатель платит переводом по реквизитам из
  `PAYMENT_DETAILS` и прикладывает чек: скриншот, PDF или ссылку. Только чек
  отправляет заказ на проверку — вам приходит он сам с кнопками «Оплата
  получена» / «Отклонить». Деньги бот не трогает.
- **platega** — оплата на странице Platega: СБП, карта или SberPay, способ
  выбирает покупатель. Чек покупателю выдаёт Platega. Подтверждение приходит
  само, без продавца — см. «Оплата через Platega».
- **demo** — оплата имитируется, ничего не списывается. Для проверки воронки.
- **stars** — инвойс в Telegram Stars (`PRICE_STARS` в звёздах, обязателен).
  Обрабатываются `pre_checkout_query` и `successful_payment`; ID платежа
  пишется в заказ и в лог — он нужен для возврата через `refundStarPayment`.

### Оплата через Platega

Подключение:

1. В `.env` на сервере: `PAYMENT_MODE=platega`, `PLATEGA_MERCHANT_ID` и
   `PLATEGA_SECRET` — из кабинета Platega, «Настройки → Интеграция и API».
   Ключ API показывается полностью один раз, сразу после «Сгенерировать».
2. `docker compose up -d --build`. В логе: «Platega подключена».
3. В кабинете Platega, поле Callback URL: `https://<домен>/api/platega/callback`
   (сейчас `https://iapki.sytes.net/api/platega/callback`) → «Сохранить».

Как идёт оплата. На экране оплаты (бот и Mini App) — сумма с акцией и
промокодом и кнопка «💳 Оплатить». По нажатию сервер создаёт транзакцию
(`POST /v2/transaction/process`, `app/platega.py`) и отдаёт ссылку на страницу
Platega; ссылка живёт 15 минут, повторное нажатие отдаёт ту же, а если цена
изменилась (промокод) — новую. В транзакцию уходят сумма, номер заказа и
Telegram ID с @username покупателя (`metadata` — для антифрода Platega).
После оплаты Platega возвращает покупателя в чат бота.

Подтверждение. Platega присылает уведомление на `/api/platega/callback` с
нашими `X-MerchantId` и `X-Secret`. Подписи у него нет, поэтому сервер
сверяет ключи и всё равно перепроверяет статус запросом `GET /transaction/{id}`:
поддельное «оплачено» заказ не подтвердит. Оплачено — заказ переходит в
«Оплата получена», покупателю приходит запрос UDID, продавцу — «💳 Оплата
получена через Platega». Повторные уведомления ничего не дублируют.

Подстраховка. Если уведомление не дошло (бот перезапускался), сервер раз в
минуту сам спрашивает статус свежих ссылок; у покупателя есть кнопка «Я
оплатил — проверить», а Mini App проверяет оплату, когда в неё вернулись из
банка.

Особые случаи — продавцу сообщение, решает он:

- оплачено меньше цены заказа (ссылку выдали до того, как убрали промокод) —
  заказ не подтверждается, проверьте и подтвердите вручную;
- оплатили уже отменённый заказ — верните деньги в кабинете Platega;
- возврат или частичный возврат (из кабинета или оспоренный банком) —
  «💸 Platega: возврат по заказу», заказ сам не меняется.

Платежи хранятся в таблице `payments` (номер транзакции, сумма, статус),
номер транзакции — ещё и в `orders.payment_ref`. Кнопки «Оплата получена» /
«Отклонить» у продавца остаются: подтвердить вручную можно и в режиме Platega.

**Вернуться на перевод с чеком** — `PAYMENT_MODE=manual` и перезапуск. Ключи
Platega можно не стирать: неоплаченные заказы сами перейдут на перевод, а
уведомления о ссылках, выданных до переключения, бот по-прежнему примет.
Тестового режима у Platega нет — первую оплату проверьте небольшой суммой
(например, промокодом) на своём аккаунте.

## Если хостинг блокирует api.telegram.org

Проверяется одной командой на сервере — ответа быть не должно только в случае блокировки:

```bash
curl -4 -sS -m 10 -o /dev/null -w '%{http_code}\n' https://api.telegram.org/
```

`000` означает, что провайдер режет трафик к Telegram: бот не сможет ни забирать
сообщения, ни отвечать. Лечится прокси — подойдёт любой HTTP или SOCKS5,
который сам до Telegram доходит:

```
TELEGRAM_PROXY=socks5://логин:пароль@1.2.3.4:1080
```

Прокси проверяется до запуска:

```bash
curl -4 -m 15 -x socks5://логин:пароль@1.2.3.4:1080 -o /dev/null -w '%{http_code}\n' https://api.telegram.org/
```

Любой код ответа, даже `404`, означает, что прокси рабочий — важно, что
соединение дошло. Если вместо этого соединение рвётся с `Connection reset by
peer`, попробуйте ту же строку со схемой `http://`: многие продавцы отдают
HTTP-прокси, а по SOCKS5 на том же порту сбрасывают соединение. После правки `.env` нужен `docker compose up -d --build`:
прокси требует библиотеку `aiohttp-socks`, она ставится при сборке образа.

Через прокси ходит только трафик к Telegram. Mini App отдаётся напрямую
через Caddy и от прокси не зависит.

## Работа продавца

В чате приходит карточка заказа с кнопками под текущий шаг. Команды:

| Команда | Что делает |
|---|---|
| `/orders` | открытые заказы (`/orders all` — все) |
| `/find NP-0001` | поиск по коду, UDID, юзернейму или ID |
| `/chat NP-0001` | переписка по заказу |
| `/reply NP-0001 текст` | ответить покупателю |
| `/log NP-0001` | история заказа |
| `/note NP-0001 текст` | заметка к заказу |
| `/stats [период]` | продажи и выручка: `/stats`, `/stats 7d`, `/stats month`, `/stats 01.10-20.10` — см. «Аналитика» |
| `/promos` | промокоды: список кнопками — код, скидка, статус |
| `/promo КОД` | карточка промокода: выключить, включить, удалить — см. «Промокоды» |

То же самое во вкладке «Продавец» в Mini App — она видна только аккаунтам из
`SELLER_IDS`; остальным API отвечает 403.

**Удаление заказа из базы.** В карточке заказа, открытой из группы «Все», есть
кнопка «🗑 Удалить из базы» — для старых и тестовых заказов. Перед удалением
витрина переспрашивает и предупреждает, если оплата по заказу подтверждалась:
такой заказ пропадёт из продаж и выручки в аналитике. Вместе с заказом каскадом
удаляются переписка, история и настройки уведомлений по нему; в журнале событий
остаётся запись `order_deleted` без привязки к заказу — кто, когда и что удалил
(код, статус, сумма). Вернуть удалённый заказ нельзя — только из бэкапа.

### Сортировка и фильтры

Под подгруппами («Открытые», «Проверить оплату», «Готовые», «Все»…) — кнопка
«Сортировка и фильтры». У каждой подгруппы свои настройки: отсортировали
«Готовые» — «Все» остаются как были. Настройки запоминаются на этом устройстве
(`localStorage` Mini App), рядом с кнопкой — «Сбросить».

| | Что есть |
|---|---|
| Сортировка | новые сверху, старые сверху, последняя активность (чек, UDID, сообщение, смена статуса), непрочитанные сверху, покупатель по алфавиту |
| Статус | в «Открытых» и «Всех», где статусов несколько: например, скрыть отменённые |
| Период создания | сегодня, 7 дней, 30 дней или свои даты; границы — по часам телефона |
| Сообщения | только заказы с непрочитанными сообщениями покупателя |
| UDID | есть или нет — в «Открытых» и «Всех» |

Считает всё сервер (`/api/seller/orders`: `sort`, `st`, `from`, `to`, `unread`,
`udid`), поэтому фильтр видит все заказы, а не только загруженные. За раз
приходит до 100 заказов; если подошло больше, под списком написано, сколько
всего. Поиск по коду, UDID или юзернейму идёт по всем заказам — настройки
подгруппы к нему не применяются.

## Работа поставщика

Поставщик ставит сертификаты, поэтому из заказа ему нужен только номер
устройства. Роль задаётся в `SUPPLIER_IDS` и не даёт ничего, кроме просмотра
UDID: ни сумм, ни платежей, ни заметок продавца, ни переписки, ни кнопок
управления заказом.

О новом заказе бот пишет сам одной строкой — `Заказ № NP-0001 от @покупатель` —
с кнопкой «Открыть заказ». В карточке пять строк: номер заказа, статус
исполнения, покупатель, время создания и UDID; кнопка «Скопировать UDID» кладёт
номер в буфер обмена силами самого Telegram.

| Команда | Что делает |
|---|---|
| `/udids` | заказы с присланным UDID |
| `/supplierhelp` | что умеет поставщик |

То же во вкладке **Поставщик** в Mini App: список заказов с UDID (статус,
время, покупатель), карточка с теми же пятью строками и кнопка «Скопировать
UDID». Ручка `/api/supplier/orders` отвечает только аккаунтам из
`SUPPLIER_IDS`, остальным — 403, и отдаёт ровно эти поля, без сумм и заметок.

Кто записан и в `SELLER_IDS`, и в `SUPPLIER_IDS`, получает оба сообщения —
карточку продавца и строку поставщика, и видит в Mini App обе вкладки. Так
владелец с одним аккаунтом на две роли видит ровно то же, что увидит отдельный
поставщик.

## Переписка по заказу

Покупатель и продавец общаются в одной ленте, привязанной к заказу. Она
доступна из двух мест сразу, и это одни и те же сообщения:

- **В Mini App** — кнопка «Чат с продавцом» на экране заказа, у продавца
  «Переписка» в карточке. Новые сообщения подтягиваются каждые 5 секунд.
- **В чате бота** — покупателю достаточно написать боту обычным текстом.
  Продавцу приходит уведомление с кнопкой «Ответить»; можно и командой
  `/reply NP-0001 текст`.

Непрочитанные показываются счётчиком на вкладках и в списке заказов продавца;
отметка «прочитано» ставится при открытии переписки.

На шаге ввода UDID бот отличает номер от вопроса по виду сообщения: строка от
16 символов из цифр, латинских букв A–F и дефиса уходит в проверку, всё
остальное — продавцу в переписку.

Сообщения лежат в таблице `messages` и удаляются вместе с заказом; по команде
`/forget` переписка покупателя удаляется, а сам заказ обезличивается.

## Команды покупателя

`/start` — витрина, `/order` — статус, `/udid` — где найти номер,
`/notify` — настройка уведомлений, `/about` — документы и реквизиты,
`/help` — помощь, `/forget` — удалить свои данные (заказы обезличиваются, см. «Аналитика»).

## Разделы Mini App

Нижний ряд: **Главная** (витрина и весь каталог с фильтрами), **Мой заказ**,
**О нас**, у продавца ещё **Продавец**, у поставщика — **Поставщик**. Каталог
живёт на главной, отдельной
вкладки «Приложения» нет: нижний ряд держим коротким, чтобы хватало места
новым разделам.

В шапке две круглые кнопки: **помощь** и **переписка с продавцом**. Помощь —
обычный экран, а не вкладка, поэтому в Telegram на ней показывается системная
кнопка «Назад».

**О нас** — место для всего, что спрашивает платёжная система: описание услуги,
документы, контакты и реквизиты. Данные берутся из `.env` (`LEGAL_*`,
`CONTACT_*`, `*_URL`), те же сведения показывает команда `/about` в боте.

Под каждым экраном витрины — подвал с реквизитами продавца, контактами
и ссылками на документы.

## Витрина без Telegram

Адрес `WEBAPP_URL` открывается и в обычном браузере: тот же каталог с ценами
и описаниями, раздел «О нас» и документы, но без заказа и переписки — вместо
кнопки покупки там «Оформить в Telegram». Это то, что увидит модерация
платёжной системы: Mini App пускает только по подписи initData, и без
публичного режима проверить магазин невозможно.

Данные для этого режима отдаёт `/api/public` — без подписи и без чужих заказов.

С ширины 900px раскладка перестраивается под компьютер: витрина шире, разделы
переезжают из нижней панели в строку слева под шапкой, каталог идёт в четыре
колонки, а ряды фильтров раскладываются в несколько строк. Баннер и текстовые
экраны выравниваются по центру страницы, каталог остаётся во всю ширину.
В шапке остаётся только логотип и две кнопки — помощь и переписка. Настройка
уведомлений в этом режиме скрыта: без подписи Telegram сервер не знает, чей
это аккаунт.

Ряды фильтров прокручиваются колесом мыши и перетаскиванием: на компьютере
пальцем их не подвинуть, а в узком окне (например, в Telegram для ПК) они
не помещаются целиком.

## Документы

Тексты лежат в `webapp/legal/*.txt` и правятся без пересборки образа: папка
`webapp` примонтирована в контейнер.

| Файл | Адрес |
|---|---|
| `offer.txt` | `/docs/offer` |
| `refund.txt` | `/docs/refund` |
| `privacy.txt` | `/docs/privacy` |
| `consent.txt` | `/docs/consent` |

Разметка простая: `# ` — заголовок, `## ` — подзаголовок, `- ` — пункт списка,
пустая строка — новый абзац. Подстановки `{{legal_name}}`, `{{inn}}`,
`{{email}}`, `{{phone}}`, `{{support}}`, `{{bot_link}}`, `{{price}}`,
`{{site}}`, `{{updated}}` заполняются из `.env` (`{{bot_link}}` — «@» и имя
бота, которое бот узнаёт у Telegram при запуске); если значение не задано,
на его месте видно `[укажите …]`. Неизвестную подстановку тесты не
пропустят: на сайте она показалась бы как есть, в фигурных скобках.

Тексты документов правит только владелец, при доработках кода они
не меняются.

Документ открывается внутри витрины, а по прямой ссылке — обычной страницей
с тем же подвалом. Согласие покупателя с офертой записывается в журнал заказа
событием `consent`.

## Оплата переводом

В режиме `manual` покупатель видит реквизиты строками: телефон для СБП, банк
получателя, получатель, номер карты, сумма к оплате и номер заказа для
комментария. Значения, которые нужно ввести в банке, копируются кнопкой
в витрине и нажатием на текст в чате бота — там они отправляются в `<code>`.
Сумма копируется без пробелов и знака рубля, её удобно вставить в приложение
банка.

Реквизиты берутся из `.env` (`PAY_*`), `PAYMENT_DETAILS` остаётся примечанием
под ними. Если ничего из `PAY_*` не задано, показывается только примечание —
как было раньше. Сумма берётся из `PAY_AMOUNT`, а без неё — из цены заказа.

Иконку банка сервер подбирает по названию из `PAY_BANK` среди иконок каталога;
`PAY_BANK_ICON` перекрывает подбор. В `webapp/brand/sbp.svg` лежит знак
из официального логотипа НСПК — без надписи, она в иконку не помещается.

### Чек об оплате обязателен

Без чека заказ на проверку оплаты не уходит. Так продавцу не приходится искать
платежи, которых не было: каждая заявка приходит уже с подтверждением.

Чек — любые файлы, вместе до 15 МБ, или ссылка (банки часто отдают чек
страницей). Формат файла не проверяется: банки и телефоны выдают чеки в самых
разных форматах.

- **в витрине** — кнопка «📎 Я оплатил — прикрепить чек» (можно выбрать сразу
  несколько файлов, до 10 штук и вместе до 15 МБ) или поле «ссылка на чек» под
  ней. Пока файлы загружаются, на кнопке виден процент и под ней — полоса;
  когда файлы дошли до сервера, кнопка пишет «Отправляем продавцу…». Продавцу
  JPEG, PNG и WebP до 10 МБ приходят фотографией, остальное — файлом. Если
  файлов несколько, они приходят по очереди с подписью «файл N из M», а
  следом — карточка заказа с кнопками;
- **в чате бота** — фото, файл, видео (например, запись экрана) или сообщение
  со ссылкой. Кнопка «Я оплатил» сама заказ не двигает, а просит прислать
  чек. Обычный текст без ссылки уходит продавцу в переписку, а бот напоминает
  про чек.

Первый чек к неоплаченному заказу и есть заявка об оплате: заказ переходит
в «Оплата на проверке», а продавцу приходит одно сообщение — чек, карточка
заказа и кнопки «Оплата получена» / «Отклонить». Чек к заказу, который уже на
проверке, просто пересылается продавцу. Если продавец отклонил оплату, заказ
возвращается к оплате, и для новой заявки нужен новый чек.

Ручка `/api/order/claim` («Я оплатил» без чека) отвечает 400 с объяснением —
её могла вызвать витрина, открытая до выкатки. Чек принимают
`/api/order/receipt` (файл) и `/api/order/receipt/link` (ссылка; её можно
вставить вместе с текстом — сервер найдёт ссылку сам).

Файлы у себя не храним: из чата они пересылаются продавцу по `file_id`,
из витрины уходят в Telegram байтами. В заказе остаётся отметка в переписке
и событие `receipt`, само хранилище чеков — переписка продавца.

Требование касается только режима `manual`: в `demo` оплата имитируется,
в `stars` её подтверждает сам Telegram.

## Приветствие

На каждый `/start` бот присылает картинку `app/assets/welcome.jpg` с подписью
(`texts.welcome`) и кнопками витрины. Когда покупатель просто открывает чат,
Telegram боту ничего не сообщает, поэтому приветствие приходит в ответ на `/start`:
первое нажатие «Начать», переход по ссылке на бота, команда из меню.

Картинка загружается в Telegram один раз, дальше бот шлёт её по `file_id`.
Если файла нет или Telegram его не принял, приветствие уходит текстом.

Заменить картинку — положить JPEG или PNG с тем же именем и пересобрать образ
(`docker compose up -d --build`): папка `app/` вшита в образ. Цена и число
приложений на картинке нарисованы — после смены `PRICE_RUB` или каталога
картинку нужно обновить, подпись обновится сама.

## Запуск без Docker

Пригодится, чтобы посмотреть проект на своей машине. `.env` читается
автоматически из корня проекта; переменные окружения, заданные снаружи, важнее файла.

```bash
python -m venv .venv && .venv/bin/pip install -r requirements.txt
python tools/preview.py            # http://127.0.0.1:8099 — UI без Telegram и токена
python -m app.main                 # живой бот: нужен .env с BOT_TOKEN и SELLER_IDS
python -m tests.smoke_test         # правила заказа + HTTP-API + подпись initData
python -m tests.bot_test           # хэндлеры бота на фейковых апдейтах
```

На Windows путь к интерпретатору — `.venv\Scripts\python.exe`.

`preview.py` поднимает только веб-часть в режиме `demo`, вход без подписи,
«сообщения в Telegram» печатаются в консоль. Токен не нужен.

`python -m app.main` работает откуда угодно, включая домашний компьютер:
бот забирает обновления сам (long polling), входящие порты и домен не нужны.
С пустым `WEBAPP_URL` весь путь заказа проходит в переписке.

## Сборки .ipa

Витрина собирается из файлов: каждая сборка в `files/` рядом с
`docker-compose.yml` — это товар. Положили файл — товар появился, убрали —
пропал. Перезапуск не нужен: бот перечитывает папку на каждом запросе.

Имя файла — `<слаг>-<версия>.ipa`. Слаг — ключ товара: латиница в нижнем
регистре, цифры и дефисы. Он же стоит в адресе скачивания и в `catalog.toml`.

```
files/sber-17.6.1.ipa
files/ozon-bank-19.27.0.ipa
```

Что бот берёт из самой сборки (`app/bundle.py`):

| Поле | Откуда |
|---|---|
| Название | русское из локализации сборки (`ru.lproj`), иначе `CFBundleDisplayName` |
| Версия | из имени файла, а если её там нет — из сборки |
| Минимальная iOS | `MinimumOSVersion` |
| Иконка | самая крупная из объявленных в `Info.plist` |
| Размер | с диска |

Категории и описания в сборке нет: без уточнений товар попадает в «Другое» и
идёт без описания. Это и любое другое поле правится в `catalog.toml`.

Для одного слага берётся самый свежий по времени файл, остальные можно оставить
запасными. Файл с именем не по шаблону бот пропускает и один раз пишет об этом
в лог.

Сборки раздаются по ссылке `https://<домен>/ipa/<слаг>`. Ссылка открытая: её
можно дать в канале, в чате бота и кому угодно ещё. Скрытый товар
(`hidden = true`) по ней не скачать.

В репозиторий сборки не попадают (`files/` в `.gitignore`): GitHub не примет
файл тяжелее 100 МБ, а история распухнет навсегда. Выкатка кода их не трогает.
С компьютера владельца сборки и `catalog.toml` отправляет скрипт
`upload_patched.py` из папки с пропатченными сборками: он шлёт только
недостающее.

Проверить, что видит сервер:

```bash
docker compose exec bot python -c "from app import catalog, config; catalog.use_folder(config.load_config().ipa_dir); print([a['slug'] for a in catalog.apps()])"
```

Caddy эти файлы не сжимает — они и так архивы. Докачка после обрыва работает:
сервер отдаёт их по частям.

## catalog.toml — уточнения к товарам

Файл `files/catalog.toml` рядом со сборками правит любое поле товара. Раздел
`[слаг]` действует на любую версию приложения, раздел `["файл.ipa"]` — только
на этот файл. Чего в файле нет — берётся из сборки. Пример со всеми нынешними
товарами — `catalog.example.toml` в корне репозитория.

```toml
[sber]
name = "СберБанк"
category = "Банки"
desc = "Счета и карты, переводы по номеру телефона, оплата услуг и QR-кодов."
order = 10

["max-26.17.3.ipa"]
version = "26.17.3 beta"
```

| Поле | Что делает |
|---|---|
| `name` | название в витрине |
| `category` | категория — фильтр над каталогом; без неё «Другое» |
| `desc` | описание; его читает покупатель и модерация платёжной системы |
| `icon` | своя картинка вместо иконки из сборки — файл рядом: `"sber.png"` |
| `color` | цвет плитки `"#21A038"` — виден, когда иконки нет |
| `dark` | `true` — тёмная буква на светлой плитке |
| `version` | версия вместо той, что в имени файла |
| `min_ios` | минимальная iOS вместо той, что в сборке |
| `order` | место в каталоге: меньше — выше |
| `hidden` | `true` — товар не показывается, файл остаётся на сервере |
| `price` | цена при заказе этого приложения отдельно через API; витрина продаёт весь каталог |

Наверху файла — два общих параметра:

- `categories = ["Банки", "Общение", ...]` — порядок фильтров. Прочие категории
  идут следом по алфавиту, «Другое» — последней. Фильтр без товаров не
  показывается.
- `featured = ["sber", "tbank", ...]` — плитки в шапке витрины. Без него —
  первые шесть товаров.

Бот перечитывает файл, как только он меняется. Ошибка в синтаксисе витрину не
роняет: бот пишет в лог и работает по последней удачной версии. Незнакомое поле
или значение не того типа пропускается с предупреждением — так ловятся опечатки:

```bash
docker compose logs bot | grep catalog.toml
```

Рабочая копия файла у владельца лежит рядом со сборками; `upload_patched.py`
проверяет её перед отправкой, а прежнюю версию на сервере сохраняет как
`catalog.toml.bak`. Правку, сделанную прямо на сервере, следующий запуск
скрипта перезапишет — переносите её в рабочую копию.

## Иконки приложений

Иконка товара берётся в таком порядке:

1. картинка из поля `icon` в `catalog.toml` — файл рядом со сборками
   (или в `webapp/icons/`);
2. иконка из самой сборки, пересобранная из формата Apple в обычный PNG —
   браузер исходный файл не открывает;
3. `webapp/icons/<слаг>.png` — запасная, например для предпросмотра, где
   сборки-пустышки без иконок;
4. буква на цветной плитке.

Витрина получает иконку по адресу `/icons/<слаг>?v=…`. Метка меняется вместе с
файлом, поэтому кэш браузера не мешает обновлению. Иконки — товарные знаки их
владельцев: право показывать их в витрине — ваша зона ответственности.

В `webapp/icons/` также лежат значки банков для страницы оплаты — они живут
независимо от каталога: получать перевод можно и на банк, приложений которого мы
не продаём. Сервер выбирает PNG, если он есть, иначе SVG.

Посмотреть, что внутри сборок, и выложить их иконки файлами:

```bash
python tools/ipa_scan.py /путь/к/папке --icons /куда/положить
```

Скрипт печатает название, версию, размер и минимальную iOS, а с `--json` отдаёт
их машинно. Разбирает сборки он тем же кодом `app/bundle.py`, что и витрина.

## Инструкция по UDID

Покупатель получает UDID прямо на телефоне, компьютер не нужен: сайт
`udid.tech` → **Get My UDID** → установка профиля в Настройках → страница

Картинка со скриншотами лежит в `webapp/img/udid-guide.webp` и показывается

## Инструкция по установке

Инструкция не пишется заново для каждого заказа: шаги лежат в шаблоне
`app/instruction.py`. Шаблон ведёт покупателя через двух ботов: @iRegerBot
(регистрация UDID и сертификат) и @isignerbot (подпись и установка).

Карточка шага повторяет присланный слайд: шапка с логотипом и счётчиком
`01 / 10`, салатовый номер, заголовок, подпись, кадр переписки в рамке,
подпись под ним, `@iApkibot` и полоса пройденных шагов. Тексты берутся
из `app/instruction.py`, оформление — из стилей, а кадр переписки лежит
картинкой в `webapp/img/instruction/step-NN.webp` (вырезка из слайда,
560×1106, WebP, около 60 КБ). Упоминания ботов в тексте становятся ссылками
автоматически.

Отправляет её одна кнопка. Продавец ставит сертификат и жмёт «Сертификат
установлен» — в чате бота или во вкладке «Продавец»: заказ закрывается, и
покупателю тут же уходит готовая инструкция. Писать продавцу нечего, поэтому
отдельного шага с текстом нет.

Первым в инструкции идёт блок «Сначала включите режим разработчика»: без него
iOS 16 и новее не запустит приложение, подписанное сертификатом разработчика.
Четыре шага текстом и картинка `webapp/img/developer-mode.jpg` (Настройки →
Конфиденциальность и безопасность → Режим разработчика). Тексты — в
`DEVELOPER_MODE` в `app/instruction.py`; оттуда их берут и витрина, и сообщение
в чате бота, где этот блок тоже стоит первым.

Дальше покупатель получает блок со ссылками на ботов, подсказкой «Где взять IPA-файлы»
со ссылкой на канал @iAppki, своим UDID и лентой из десяти карточек. Текст
подсказки и имя канала — в `SOURCES` и `CHANNEL` в `app/instruction.py`; оттуда
их берут и витрина, и сообщение в чате бота.

Лента работает как страницы в мобильном приложении: на экране ровно один шаг,
соседний приходит свайпом, перетаскиванием мышью, боковым движением трекпада
или стрелками на клавиатуре. Короткого движения достаточно — карточка
переключается целиком. Обычное колесо мыши над лентой прокручивает страницу.
На компьютере лента держит ширину телефона и стоит по центру.

В чат бота уходит тот же порядок шагов текстом — карточки остаются в витрине.

Чтобы поменять текст шага, правьте `app/instruction.py` — и витрина, и бот
берут его оттуда. Чтобы заменить кадр, положите новый файл с тем же именем
в `webapp/img/instruction/`: папка примонтирована, пересборка не нужна.

## Анимации

Витрина двигается, но не мешает: всё на `transform` и `opacity`, чтобы не
тормозить на слабых телефонах, а при системной настройке «уменьшить движение»
анимации отключаются целиком (и счётчики, и конфетти).

- При входе на экран строки списков, реквизиты, шаги заказа и карточки
  показателей поднимаются волной; перерисовка того же экрана волну не повторяет.
- Шкала заказа: пройденные шаги соединены линией, которая прорастает вниз,
  галочки выскакивают, текущий шаг пульсирует кольцом; текущий этап в ленте
  шагов светится.
- Акция: ярлык «дышит», огонёк горит, старая цена зачёркивается на глазах.
- Аналитика: столбики выручки и полоски статусов вырастают, числа набегают.
- Конфетти и вибрация, когда покупатель видит, что заказ продвинулся до
  «Оплата получена» или «Готово» (последний виденный статус помнит устройство).
- Копирование отвечает вспышкой кнопки, новые сообщения в переписке въезжают,
  выбранная вкладка подпрыгивает, тост выезжает пружинкой, в ленте инструкции
  текущий шаг крупнее соседних.

В самом боте — полноэкранные эффекты Telegram: 🎉 к «Оплата получена» и к
инструкции, 🔥 к приветствию во время акции (`const.EFFECT_*`). Клиент без
поддержки эффектов просто покажет сообщение; если Telegram эффект отклонит,
сообщение уйдёт без него.

## Аналитика

Только продавцам (`SELLER_IDS`): команда `/stats` в боте и раздел «Аналитика»
во вкладке «Продавец» в Mini App (переключатель «Заказы | Аналитика | Промокоды»). Считает
модуль `app/analytics.py`, API — `/api/seller/analytics`.

- **Продажа** — заказ с подтверждённой оплатой; дата продажи — дата
  подтверждения (`orders.paid_at`). Тестовые заказы (`TEST_IDS`) и демо-оплата
  не считаются.
- **Выручка** — сумма цен проданных заказов. Цена хранится в заказе, поэтому
  смена `PRICE_RUB` и акции прошлые продажи не меняет. Средний чек — выручка,
  делённая на число продаж.
- **Отменено после оплаты** — продажи, заказ по которым потом отменили:
  показываются отдельной строкой вместе с итогом «без отменённых».
- **Заказы по статусам** — заказы, оформленные за период, по их текущему
  статусу, с долями; «Дошли до оплаты» — доля оформленных, по которым оплату
  подтвердили. Отмены разделены на «до оплаты» и «после оплаты».
- **Периоды:** сегодня, 7 и 30 дней, этот месяц, всё время, свои даты. Сутки —
  по Москве. Выбранный период помнит устройство.
- **Свои даты** — с 01.01.2020 по сегодня; конец в будущем обрезается до
  сегодня, дата раньше 2020 года или начало в будущем — ошибка «проверьте год».
  Поле даты присылает изменение на каждую цифру (пока набирают 2026, в нём
  бывают 0002, 0020 и 0202), поэтому витрина применяет дату, когда набор затих
  или нажат Enter, и только настоящую; отчёт перерисовывается без полей, так
  что набор во втором поле не обрывается. Так же работают даты в фильтре заказов.
  Сохранённый на устройстве период с опечаткой в годе при открытии сбрасывается
  на «Всё время».
- **Список продаж.** Нажатие на любую карточку показателя открывает заказы, из
  которых он сложился (`/api/seller/analytics/orders`): номер, время оплаты по
  Москве, сумма, промокод, покупатель; отменённые после оплаты помечены. Нажатие
  на заказ — его карточка, «Назад» возвращает к списку.
- **График продаж** по дням (больше 62 дней — по месяцам): высота столбика —
  число продаж, слева шкала, снизу подписан каждый день. Длинный период
  листается вбок и открывается на последних днях. Нажатие на столбик — продажи
  этого дня (месяца).

В `/stats` период задаётся словом (`today`, `7d`, `30d`, `month`, `all`,
по-русски тоже: `сегодня`, `неделя`, `месяц`, `всё`) или датами:
`01.10-20.10` (текущий год), `01.10.2026-20.10.2026`, `2026-10-01..2026-10-20`,
одна дата — один день. Без периода — всё время.

**`/forget` обезличивает, а не удаляет.** Иначе проданные заказы пропали бы из
выручки. Заказы покупателя переходят на служебного «Удалённого покупателя»
(`users.tg_id = 0`); из них стираются UDID, заметка продавца и ссылка на платёж,
удаляются переписка и записи о чеках, Telegram ID покупателя убирается из журнала
событий. Остаются номер, сумма, даты и статусы. Сам пользователь и его настройки
удаляются.

## Тестовые заказы

Команда проверяет бота, оформляя заказы от своих аккаунтов, — чтобы такие
заказы не топили уведомления о настоящих, перечислите эти аккаунты в
`TEST_IDS` (через запятую). Заказ от аккаунта из списка при создании
помечается тестовым (`orders.is_test`), пометка остаётся навсегда.

- Покупателю, то есть самому тестировщику, всё приходит как обычно.
- Уведомления продавца и поставщика о тестовом заказе получает только сам
  тестировщик — если он записан в `SELLER_IDS` или `SUPPLIER_IDS`. Первая
  строка таких сообщений — «🧪 Тестовый заказ». Остальным не приходит ничего.
- В Mini App и в `/orders`, `/udids` тестовый заказ помечен 🧪; в «Сортировке
  и фильтрах» продавца есть «🧪 Скрыть тестовые».
- Счётчики подгрупп, точка на вкладке «Продавец» и аналитика (`/stats`,
  раздел «Аналитика» в Mini App) тестовые заказы не считают.

Работать с тестовым заказом за продавца можно, как обычно, из Mini App.
Заказы, оформленные до появления `TEST_IDS`, остаются обычными.

## Жизненный цикл заказа

Один открытый заказ на покупателя. Выполненный заказ новому не мешает:
на его экране есть кнопка «Оформить новый заказ», а сам заказ можно закрыть —
кнопкой «Закрыть заказ» у покупателя или 🗂 у продавца.

Покупатель, закрыв выполненный заказ, лишь убирает его со своего экрана:
статус остаётся «Готово», у заказа появляется отметка `closed_at`, продавцу
приходит «🗂 Покупатель закрыл заказ». Вопрос «Закрыть заказ?» витрина задаёт
прямо на странице — системное окно Telegram есть не во всех клиентах.

Заказ в работе (оплачен, но не выполнен) покупатель отменить не может —
это делает продавец, чтобы оплаченная работа не пропадала по случайному нажатию.

Статус «Готовим инструкцию» (`installed`) остался только у заказов, заведённых
до того, как установка и отправка инструкции стали одной кнопкой. У такого
заказа продавец видит кнопку «Отправить инструкцию» — она делает то же самое.

**Автоотмена неоплаченных.** Заказ «Ожидает оплаты», по которому
`ORDER_TTL_DAYS` дней (по умолчанию 3) ничего не происходит, бот отменяет сам.
«Ничего не происходит» — не менялся `updated_at`: его сдвигают сообщение в
переписке, промокод, смена товара или цены. За сутки до отмены покупателю
приходит напоминание с кнопками оплаты, при отмене — «Заказ отменён: оплаты не
было 3 дня». Заказ, который завис ещё до включения автоотмены (или пока бот не
работал) и напоминания не получал, отменяется молча. Применение промокода при
отмене возвращается в лимит. Заказы с чеком («Проверяем оплату») и оплаченные не
трогаются; чек, пришедший в ту же секунду, отмену останавливает. Проверка —
раз в десять минут; в истории заказа — «автоотмена: нет оплаты 3 дня».
`ORDER_TTL_DAYS=0` выключает автоотмену.

## Акция

Скидка задаётся в `.env` и не требует правок кода:

```
PRICE_RUB=3000                     # обычная цена
PROMO_PRICE_RUB=1500               # цена по акции
PROMO_UNTIL=30.11.2026             # последний день акции, по Москве; пусто — бессрочно
PROMO_LABEL=-50% в честь открытия  # подпись; пусто — «Скидка 50%»
```

Пока акция идёт, покупатель платит `PROMO_PRICE_RUB`, а рядом видна зачёркнутая
обычная цена: в приветствии и оформлении заказа в боте, в реквизитах («Скидка уже
учтена»), на главном экране витрины (ярлык со сроком), в оформлении (строка
«Скидка»), на экране оплаты и в «О нас». Кнопка в приветствии — «Оформить со
скидкой −50%». Процент считается сам. Описание бота в профиле (до «Старт») бот
выставляет сам и меняет при начале и конце акции — правки в BotFather
перезаписываются. Цена в оферте (`{{price}}`) — та, что платят сегодня.

Со дня после `PROMO_UNTIL` пометки акции исчезают и цена сама возвращается к
`PRICE_RUB` — перезапуск не нужен. Неоплаченный заказ без чека всегда стоит по
текущей цене: он пересчитывается, когда покупатель открывает заказ или прикладывает
чек. Заказ с чеком хранит цену, по которой заявлена оплата.

## Промокоды

Закрытые промокоды: витрина их не показывает, публикуем сами, где и когда нужно.

**Как покупатель применяет промокод.**

- **Mini App:** поле «Промокод» на экране оформления — сервер сразу показывает
  скидку и сумму «К оплате», а применение занимается вместе с оформлением заказа.
  На экране оплаты — «🎟 У меня есть промокод», пока чек не отправлен; там же
  «Убрать».
- **Бот:** под реквизитами кнопка «🎟 Ввести промокод», код присылается
  сообщением; бот отвечает новой суммой. Если вместо кода пришёл вопрос, он
  уходит продавцу как обычное сообщение. Применённый код убирается кнопкой
  «✖️ Убрать промокод».
- Отказ — с причиной: такого промокода нет, срок истёк, применения закончились,
  промокод не действует (выключен), начнёт действовать такого-то числа, «вы уже
  использовали этот промокод» (лимит на покупателя). После 10 неудачных попыток
  за 15 минут — пауза: перебором коды не подобрать.
- После чека промокод не сменить и не убрать: продавец сверяет оплату с суммой.
- При оплате Stars промокоды не действуют: цена в звёздах одна (`PRICE_STARS`).
- `PAY_AMOUNT` из `.env` о скидке не знает — у заказа с промокодом к оплате
  всегда цена заказа.

**Лимиты.** Применение занимается сразу, как покупатель применил код, — лимит
«всего» не превысится, даже если двое нажмут одновременно. Оно возвращается, если
покупатель убрал промокод, заказ отменили до оплаты или продавец удалил заказ.
Отменённый до оплаты заказ хранит код и скидку для истории («применение
возвращено»); отменённый после оплаты применение не возвращает.

**Цена.** Применённый промокод остаётся за заказом до оплаты, даже если его потом
выключили или срок вышел. Цена неоплаченного заказа по-прежнему пересчитывается
от текущей (кончилась акция — 3 000 ₽ − 20% = 2 400 ₽). Если скидка в рублях
станет не меньше новой цены, промокод снимается сам: бесплатных заказов нет.
В заказе хранятся `promo_id`, `promo_code` и `promo_discount`; `price_rub` — уже
со скидкой, поэтому аналитика считает выручку по фактической сумме.

**Что видит продавец.** Строку «Промокод: КОД · −300 ₽ (без него 1 500 ₽)» в
карточке заказа и в подписи к чеку, 🎟 в списке заказов Mini App; в карточке
промокода — заказы с ним (нажатие открывает карточку заказа, «Назад» — обратно
к промокоду) и историю применений и возвратов.

**Форма промокода.** Кнопка с круговой стрелкой справа от кода — другой
случайный код. «В процентах / в рублях» — переключатель с переезжающей
подсветкой, как «Заказы | Аналитика | Промокоды». Срок задаётся датами «с» и
«по» или в одно нажатие: бессрочно, 7 дней, 30 дней, до конца месяца (с
сегодняшнего дня по Москве). Лимиты — «всего» и «на покупателя», пусто — без
лимита.

Управляют все продавцы из `SELLER_IDS`:

- **Mini App** → «Продавец» → «Промокоды»: список с фильтром по статусу, создание,
  правка условий, выключатель, удаление и карточка с историей изменений.
- **Бот**: `/promos` — список, `/promo КОД` — карточка с кнопками «Скопировать
  код», «Выключить» / «Включить», «Удалить». Создавать и менять условия — в Mini App.

Что задаётся у промокода:

| Поле | Правило |
|---|---|
| Код | латиница, цифры и дефис, 4–32 знака, хранится заглавными. «🎲» даёт случайный `IAPKI-XXXXXX-XXXXXX` без похожих 0/O и 1/I/L. **После создания не меняется** |
| Скидка | в процентах (1–99) или в рублях (меньше текущей цены). Бесплатных промокодов нет |
| Срок | «с» и «по» — даты по Москве, обе включительно; пусто — без ограничения |
| Всего применений | пусто — без лимита |
| На одного покупателя | по умолчанию 1 раз; пусто — без ограничений |
| Включён | выключенный не действует, даже если срок идёт |
| Заметка | для продавцов: где опубликован, для кого |

Статус не хранится, а считается: «Выключен» → «Истёк» → «Исчерпан» → «Ещё не
начался» → «Активен».

**Вместе с акцией.** Промокод считается от цены, которую платят сегодня: во время
акции — от цены по акции. 3 000 ₽ − 50% = 1 500 ₽, промокод 20% → **1 200 ₽**.
Карточка показывает цену с промокодом сейчас и после акции. Если скидка в рублях
окажется не меньше цены (например, цену снизили), карточка пишет «не сработает».

**Удаление.** Промокод без применений (счётчик «применён» — 0, в том числе когда
все применения вернулись) удаляется насовсем вместе с историей; в журнале событий
остаётся запись `promo_deleted` — кто, когда и какой код удалил. Промокод, который
занимает хоть один заказ, удалить нельзя, только выключить: иначе из заказов
пропадёт, откуда скидка. Лимит «всего» нельзя сделать меньше занятых применений.

Хранение: таблица `promo_codes`, история — в `events` с колонкой `promo_id`
(миграция добавляет её в старую базу сама). Правила и расчёт — `app/promocodes.py`.

## Каталог покупается целиком

Цена одна на весь каталог — `PRICE_RUB`. Поэтому в карточке приложения вместо
цены стоит «Входит в полный доступ», а нажатие на любую карточку открывает то же
оформление, что и кнопка «Весь каталог»: отдельные приложения в витрине не
продаются.

Сам заказ по-прежнему умеет хранить выбранное приложение (`orders.app_slug`):
так устроены заказы, заведённые до этой правки, и ручка `/api/order/create`,
которая принимает поле `app`. Продавец видит такой выбор строкой «Товар», а своя
цена приложения задаётся полем `price` в `catalog.toml`:

```toml
[spotify]
price = 990
```

Если покупатель передумал до оплаты, его неоплаченный заказ просто переключается
на новый выбор. Заказ, по которому уже прислан чек об оплате, не меняется — деньги
могли уйти за другой товар.

## Уведомления

Каждый решает сам, что присылать ему в чат бота. Настройки живут в Mini App
(«Помощь» → «Настроить уведомления») и в боте по команде `/notify`.

Покупателю доступны два переключателя — статус заказа и сообщения продавца.
Продавцу пять: новые заказы, оплаты, полученные UDID, сообщения покупателей,
запросы помощи. Поставщику один — новые заказы.

Поверх общих настроек работает режим **для конкретного заказа**:

| Режим | Что делает |
|---|---|
| По общим настройкам | обычное поведение |
| Всегда уведомлять | шлём, даже если вид выключен целиком |
| Не беспокоить | молчим по этому заказу, остальные приходят как обычно |

Настройка заказа сильнее общей — так можно выключить, например, все оплаты и
оставить только один заказ, за которым следите. У продавца режим переключается
кнопкой 🔔 в карточке заказа, у покупателя — на экране настроек.

Выключенное уведомление не теряет данные: статус заказа и инструкция всегда
остаются в Mini App, просто не приходят сообщением.

### Номер заказа за сутки

В сообщениях продавцу и поставщику — карточки, уведомления, чеки, переписка,
`/log` — к номеру заказа дописан его номер за сутки: `Заказ NP-0155 (4)` —
четвёртый заказ за день. Покупатель его не видит: по нему видно, сколько
у магазина заказов. Списки `/orders`, `/udids` и Mini App показывают обычный номер.

- Сутки одни на всю команду — **по Новосибирску** (`ORDER_DAY_TZ` в `app/const.py`).
  Свои сутки каждому не делаем: тогда у одного заказа у продавца в Москве и
  поставщика в Магадане были бы разные номера.
- Номер выдаётся при создании заказа и больше не меняется. Удалили заказ —
  номера остальных не сдвигаются и не повторяются.
- У тестовых заказов свой счёт: они не сбивают настоящий.
- Заказам, созданным до обновления, номер проставляется при первом запуске
  по тем же правилам.

## Что стоит знать

- **UDID — персональные данные.** Он хранится в открытом виде (продавцу нужен
  рабочий номер), покупателю показывается замаскированным, `/forget` стирает
  его из заказов. Если сервисом будет пользоваться кто-то кроме вас,
  опишите это в условиях заказа.
- **Длина UDID не проверяется — только символы.** Старые iPhone сообщают
  40 hex-символов, iPhone XS и новее — 25 символов с дефисом
  (`00008150-000914312E78C01C`). Принимаются цифры, латинские буквы A–F в
  любом регистре и дефис, не длиннее 40 символов (столько вмещает поле).
  Номер хранится таким, каким его прислал покупатель, — с дефисом и в его
  регистре. Исправляется только то, что глазом не отличить: убираются пробелы,
  переносы и невидимые символы, кириллические А, В, С, Е (и строчные) меняются
  на латинские, тире и минус — на дефис. Поле в витрине делает то же самое
  прямо при вводе. Правила — в `app/udid.py`.
- **Базы, созданные до перехода на UDID, мигрируют сами** при первом запуске:
  колонки `imei`/`imei_at` переименовываются, старый статус заказа обновляется,
  в старые базы добавляются колонки `app_slug` и `closed_at`.
- **Один открытый заказ на пользователя.** Выполненный заказ не блокирует
  следующий — см. «Жизненный цикл заказа».
- Подпись `initData` проверяется на каждый запрос к API, срок жизни —
  `INIT_DATA_TTL`. Панель продавца дополнительно сверяется с `SELLER_IDS`,
  вкладка поставщика — с `SUPPLIER_IDS`.
